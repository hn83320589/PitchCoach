# 11　設計取捨與踩坑紀錄

本章保存最難從程式碼本身看出來的知識：當初在幾個方案之間怎麼選、付出什麼代價，以及開發中真的踩過的坑。素材來自設計文件的決策表、`fix` 類 commit 與開發對話。

---

## 第一部分：設計取捨

### 取捨 1：偵測演算法用 MPM，再加諧波精修

- **決策**：基頻偵測的演算法。
- **選項**：MPM、YIN；實作後又比較了「只用 MPM」與三種諧波精修的權重。
- **選擇與理由**：MPM 粗估＋sine 窗加權的諧波最小平方精修。MPM 的 clarity 天然提供「有無明確音高」的判準，對純正弦無偏；但只用 MPM 時 SNR 20 dB 誤差達 8 cents，所以加上精修（08 章 8.1–8.2）。
  > 📄 依據：`docs/ARCHITECTURE.md` D1、§4.5 的變體比較表
- **代價**：實作複雜度大增（`HarmonicFrequencyRefiner` 近 270 行，含 Dirichlet kernel、Cholesky、Brent）；每次偵測約 0.27 ms，比只用 MPM 貴很多，但仍在 IO 執行緒的預算內。

### 取捨 2：在 IO 執行緒直接偵測

- **決策**：偵測要在哪個執行緒執行。
- **選項**：`installTap`（延遲大）；`AVAudioSinkNode` 在 IO 執行緒偵測；ring buffer＋獨立分析執行緒。
- **選擇與理由**：`AVAudioSinkNode`，在 IO 執行緒偵測，以 trylock 信箱交給主執行緒。每 hop 的計算量遠小於 IO 預算，省掉跨執行緒喚醒，延遲最低。
  > 📄 依據：`docs/ARCHITECTURE.md` D2、§3.3「為什麼直接在 IO 執行緒做 MPM」
- **代價**：偵測與合成程式碼必須遵守即時規則（不配置記憶體、不等鎖），所有緩衝預先配置；Swift 6 的隔離陷阱也因此出現（踩坑 2）。設計文件保留了退路：若 overrun 就改成分析執行緒，介面不變。實機上沒有需要。

### 取捨 3：收音固定用內建麥克風

- **決策**：戴耳機時用哪顆麥克風收音。
- **選項**：固定內建麥克風、藍牙只用 A2DP；跟隨系統（有耳機麥克風就用）。
- **選擇與理由**：固定內建麥克風。三種輸出路由都用同一顆麥克風，才能滿足「讀數差 ±3 cents」；HFP 會降到 16 kHz。
  > 📄 依據：`docs/ARCHITECTURE.md` D3、§3.1
- **代價**：用藍牙耳機時，學生要對著手機唱或演奏，不能對著耳機；延遲校正時要把耳機貼近手機的麥克風。實機驗收時使用者一度以為是 AirPods 麥克風在收音，為此在延遲面板加了輸入／輸出埠的顯示（commit `eb19485`）。

### 取捨 4：音階到位容許 50 ms 的抖動

- **決策**：音階「持續 300 ms」遇到短暫超出範圍時怎麼算。
- **選項**：≤ 50 ms 的空檔不重設；任何超出即重設。
- **選擇與理由**：容許 50 ms。兒童的音常在 ±15 邊界附近抖動，嚴格重設會讓學生「明明很準卻一直不跳」。
  > 📄 依據：`docs/ARCHITECTURE.md` D5 與 §7.2 的說明
- **代價**：規則較複雜，需要額外的邊界測試（50 ms 不重設、51 ms 重設）；明顯飄走但每次都在 50 ms 內回來的音也可能過關。

### 取捨 5：中斷的練習怎麼進趨勢

- **決策**：被中斷的練習是否計入各項統計。
- **選項**：分鐘數與各音偏差計入、長音準確率不計入；全部計入；全部排除。
- **選擇與理由**：分開處理。練習量就是練習量；但中斷的長音時間短，準確率比例會失真。
  > 📄 依據：`docs/ARCHITECTURE.md` D8
- **代價**：不同指標的母體不同，讀週報時要知道這個規則（週報頁尾有說明）。

### 取捨 6：手寫 Xcode 專案檔

- **決策**：Xcode 專案怎麼產生。
- **選項**：手寫 `project.pbxproj`（資料夾同步群組）；引入 XcodeGen。
- **選擇與理由**：手寫。本機沒有 XcodeGen／Tuist，開發規範要求不擅自引入新工具；Xcode 16 的資料夾同步群組讓新增檔案不必改專案檔。
  > 📄 依據：`docs/ARCHITECTURE.md` D9、§2.2
- **代價**：專案設定（例如 Info.plist 鍵值、簽章）要直接編輯 pbxproj，沒有宣告式設定檔可讀。

### 取捨 7：歌唱邏輯放在新模組

- **決策**：歌唱判定的程式碼位置。
- **選項**：新增 `SingingEngine` target；全部放進 `PracticeEngine`。
- **選擇與理由**：新模組。歌唱的概念（音符、時間軸、顫音）和樂器練習差很多，放進 `PracticeEngine` 會讓它膨脹。
  > 📄 依據：`docs/SINGING_MODE.md` D-S1
- **代價**：`PracticeEngine` 要依賴 `SingingEngine` 才能統計歌唱紀錄，相依圖多一條邊。

### 取捨 8：時間對齊加上依路由的回授校正

- **決策**：伴奏與收音怎麼對齊。
- **選項**：host time 共同時鐘＋iOS 回報延遲＋依路由的回授校正；只用 iOS 回報的延遲。
- **選擇與理由**：加上回授校正。iOS 回報的藍牙延遲是估計值，可能差數十 ms。實機量測證實：iOS 少算了藍牙約 55 ms、喇叭約 25 ms（08 章 8.6 節）。
  > 📄 依據：`docs/SINGING_MODE.md` D-S2、§7.2；`docs/TEST_REPORT.md` §5.3
- **代價**：多一個使用者要操作的「延遲校正」畫面；用藍牙時要把耳機貼近麥克風；校正值是常數，無法追蹤延遲漂移。

### 取捨 9：喇叭外放時用回音消除，並準備退路

- **決策**：喇叭播放提示音時，怎麼避免偵測器鎖定提示音。
- **選項**：A：voice processing 回音消除＋鋼琴式提示音；B：只用快速衰減的提示音並建議戴耳機；C：喇叭時不播提示音。
- **選擇與理由**：A，不理想時退回 B。後來在模擬器上發現 voice processing 會讓引擎自己停下，於是加上自動退回 B 的守門員（踩坑 6）。
  > 📄 依據：`docs/SINGING_MODE.md` D-S3、§8 實作補充
- **代價**：回音消除會讓延遲校正無法進行（校正時要暫時關閉）；實機上的實際效果尚未驗證。

## 第二部分：踩坑紀錄

### 踩坑 1：時間戳的浮點誤差

- **症狀**：以浮點秒數換算的時間戳有微小誤差，例如 1.92 秒換成奈秒變成 1,919,999,999，讓 299／300 ms 這類精確的邊界比較不可靠。
- **原因**：二進位浮點數無法精確表示多數十進位小數；乘上 10⁹ 再截斷會少 1。
- **解法**：時間一律用 `Duration`；樣本位置換算時，取樣率為整數就用 128 位元整數運算（`multipliedFullWidth`／`dividingFullWidth`），見 `Packages/PitchCoachKit/Sources/PitchDetection/StreamingPitchAnalyzer.swift`（commit `48baf3f`）。測試輔助函式把秒換成奈秒時改為先四捨五入，註解寫明「避免 1.92e9 截成 1919999999」（`Packages/PitchCoachKit/Tests/SingingEngineTests/SingingTestSupport.swift`）。
- **教訓**：有精確邊界的規則，從資料型別就要選能精確比較的表示法；連測試的輔助函式也要注意。

> 📄 依據：commit `48baf3f` 說明「時間戳以樣本位置換算，取樣率為整數時用整數全寬乘除，Duration 精確」；測試輔助函式的註解

### 踩坑 2：IO 回呼被推斷為 MainActor 而當機

- **症狀**：App 一開始收音就終止，錯誤指向隔離檢查。
- **原因**：在 `@MainActor` 的 `AudioPipeline` 方法中建立音訊回呼 closure，Swift 6 推斷該 closure 隸屬 MainActor；iOS 在 IO 執行緒呼叫它，執行期隔離檢查失敗。
- **解法**：在非隔離的環境建立回呼：`PitchCoach/Audio/AudioNodeFactory.swift` 的靜態方法、`RealtimeCaptureContext.makeSinkNode()`。
- **教訓**：開發後期為了診斷問題，臨時在 `AudioPipeline` 加了一段錄音用的 tap closure，同一個問題立刻重現。程式註解中的教訓會被忘記；把建立即時回呼的地方集中在少數工廠函式，才能讓錯誤寫法不容易出現。

> 📄 依據：`AudioNodeFactory` 的註解「M4 曾發生」；後期重現的過程記錄在開發對話中

### 踩坑 3：SwiftData 存檔時當機

- **症狀**：使用者回報存檔時當機，當機報告指向 `PracticeRepository.save`。
- **原因**：`ModelContext` 對 `ModelContainer` 只是弱參照。只保留 context 時，container 可能被釋放，之後存檔就當機。
- **解法**：`PracticeRepository` 改為持有 container，context 從它取得（`PitchCoach/Persistence/PracticeRepository.swift`）。
- **教訓**：框架物件之間的參照強弱不一定直觀；修好後在程式中寫下原因，避免下一個人把它「簡化」回去。

> 📄 依據：開發對話中使用者提供的當機報告；`PracticeRepository` 的註解「ModelContext 對 container 只是弱參照」

### 踩坑 4：練習畫面打開是空白

- **症狀**：使用者回報進入長音、音階練習時畫面與導覽標題都是空白。
- **原因**：ViewModel 原本是 optional，在 `.onAppear` 才建立；model 為 nil 時 `Group` 沒有子 View，空的 `Group` 不會渲染，`.onAppear` 永遠不觸發。
- **解法**：改用 `@State` 直接建立 ViewModel；需要 `modelContext` 的存檔函式改在畫面出現時注入；未注入就結束練習時顯示儲存失敗訊息（commit `1600183`）。
- **教訓**：在 SwiftUI 中，「等畫面出現再建立狀態」與「畫面要有內容才會出現」可能形成死結。

> 📄 依據：commit `1600183` 說明；使用者的截圖回報

### 踩坑 5：KTV 音高條不重繪

- **症狀**：歌唱時學生的音高曲線一直沒出現。從 UI 測試的截圖發現。
- **原因**：`TimelineView` 每幀更新，但 `Canvas` 的繪圖閉包沒有用到 `timeline.date`，SwiftUI 判斷內容沒變而不重繪。
- **解法**：把 `timeline.date` 傳進繪圖函式（`PitchCoach/Features/Singing/PitchRollView.swift`）。
- **教訓**：SwiftUI 依「輸入是否改變」決定是否重繪；靠外部可變狀態（例如每幀增加的音高點）繪圖時，要讓變化反映在輸入上。UI 測試的截圖除了當文件，也能抓到這種「不會報錯、只是不顯示」的問題。

> 📄 依據：commit `00bda0a` 說明「Canvas 需以 timeline.date 為輸入，否則 SwiftUI 不重繪」

### 踩坑 6：回音消除讓引擎無限重啟，演唱卡在「預備…」

- **症狀**：在模擬器以真實收音進入歌唱練習，畫面停在「預備…」，主控台不斷出現 `engineConfigurationChanged → restart`。
- **原因**：開啟 voice processing 的引擎啟動約 0.1 秒就自己停下並發出設定變更通知；App 每次都照常重建，每 0.45 秒循環一次。伴奏播放器跟著引擎重建，新的播放器沒收到播放指令，「歌曲開始」永遠不會回報。UI 測試用合成輸入不經過引擎，所以沒抓到。
- **解法**：`VoiceProcessingGuard` 在「開啟回音消除的引擎啟動後 1 秒內自己停下」連續 2 次時停用該路由的回音消除；`AudioInterruptionPolicy` 加入 `isSongPlaying`，伴奏播放中的引擎重建會中斷演唱並保留已唱完的音（commit `eb260fb`）。
- **教訓**：「收到通知就重建」若重建本身會觸發同一個通知，就是正回饋迴圈；自動重試一定要有次數上限與退路。合成輸入的測試捷徑也是盲點。

> 📄 依據：commit `eb260fb` 說明；開發中以臨時診斷記錄確認「發出通知的是目前這顆引擎本身」

### 踩坑 7：同音連唱給出假的節奏判定

- **症狀**：學生把「C C」連成一個長音時，第二個 C 在一般速度被判「提早約 250 ms」，200 BPM 時反而被判「準時」。
- **原因**：三種起音線索都不存在，退回規則「取搜尋範圍內第一個接近目標音的 frame」取到的是前一個音的 frame。
- **解法**：前一個音同音高、且跨過樂譜起點時發聲沒有中斷時，回報 `notSeparated`「沒有分開唱」，不計入節奏正確率（commit `cd38059`）。修正前先讓測試以「行為錯誤」失敗，紅燈結果與審查推論一致（09 章 9.8 節）。
- **教訓**：退回規則是所有正常路徑都失敗時才執行的程式碼，最容易藏錯誤的假設。量不到時回報「不知道」。

> 📄 依據：使用者貼上的程式碼審查意見（靜態推論）；使用者決定「標『沒有分開唱』，不計入」；commit `cd38059`

### 踩坑 8：「我唱很高，卻被判偏低」——判定其實是對的

- **症狀**：使用者反映已經唱得很高，結果仍是偏低。
- **調查**：先懷疑判定本身。過程中一度觀察到「準確的提示音全部被判偏低 350–950 cents」，在回報中錯誤地下了「問題出在系統」的結論；之後分析錄音才發現麥克風收到的主要是人聲，不是提示音，隨即更正。最後的交叉檢驗：
  - 離線合成〈兩隻老虎〉的提示音直接餵給偵測器：32 個音全部 0 cent。
  - 錄下麥克風輸入，用獨立的頻譜分析比對：每個時間點一致。
  - 使用者 5 次紀錄的偏差中位數 −348 到 −781 cents，每次不同、也不是整整一個八度。
- **結論**：判定正確，使用者是用自己習慣的調在唱，比目標低 3.5–8 個半音。程式沒有修改。
- **教訓**：面對「判定不準」的回饋，要用可重現的交叉檢驗回答；還沒有證據之前，不要急著下結論。錄音分析中「聲音開頭有往上滑」「旋律走向一致但偏移量不固定」這類特徵，是區分人聲與系統誤差的線索。

> 📄 依據：開發對話中的調查過程與更正；`docs/TEST_REPORT.md` §6.3

### 踩坑 9：練習頁無法恢復收音

- **症狀**：實機測試鬧鐘中斷時，長音練習頁顯示灰色的「開始」與「收音尚未啟動。」，沒有恢復的方法。
- **原因**：收音被中斷後進入「暫停」狀態；iOS 不一定在中斷結束時建議恢復，這時只有調音器頁有「恢復收音」按鈕。練習頁只看「是否 running」，其他狀態一律顯示同一句話，說法也不正確。
- **解法**：`AudioUnavailableNotice` 把收音狀態對應成提示與動作（暫停→恢復收音、失敗→重試、沒有權限→前往設定），三個練習頁共用（commit `4a590eb`）。
- **教訓**：狀態機的每個狀態，在每個畫面上都要有出口。模擬器無法觸發「中斷結束但未建議恢復」，實機測試才看得到。使用者事後也指出，因為進入 App 時系統通常已先暫停其他 App 的音樂，這個按鈕實際出現的機會不多；決定保留。

> 📄 依據：使用者的實機截圖與「可以修」的回覆；commit `4a590eb`

### 踩坑 10：週報說明漏了歌唱

- **症狀**：實機產生的 PDF 寫「以及長音、音階練習 2 分 58 秒」，但這個數字也包含歌唱時間。
- **原因**：說明文字是加入歌唱模式之前寫的；測試只檢查數字，沒檢查說明文字。
- **解法**：改為「以及長音、音階、歌唱練習」，PDF 文字抽取測試加入這段的檢查（commit `01c8989`）。
- **教訓**：新增功能時，要回頭找「列舉了既有功能」的文字與程式。

> 📄 依據：實機截圖 `docs/device/ac13-pdf-in-files.png`；commit `01c8989`

## 潛在風險

> 🔍 以下為推斷，開發中沒有實際發生：

- **延遲校正值不會過期**：耳機韌體更新或延遲漂移後，舊的校正值會讓節奏判定系統性地偏移。
- **電平門檻在實際教室環境**：樂器離手機較遠、教室有其他學生的聲音時，−50 dBFS 門檻可能讓讀數時有時無，或把其他人的聲音當成音高。
- **長歌曲的記憶體**：`SingingEvaluator` 保存整首的 frame，曲目很長時記憶體線性成長。
