# 01　需求分析：從題目到可驗收的需求

本章記錄這個系統要解決什麼問題，以及題目中模糊的地方是怎麼被轉成可測試的規則。需求是最容易被事後腦補的部分，所以每一項都標示來源。

---

## 1.1 背景與目標

> 📄 依據：開發對話中使用者提供的原始題目；`docs/ARCHITECTURE.md` §1.1

兒童小提琴與長笛教室的學生在家練習時，缺少即時的音準回饋；老師上課時也看不到學生一週練了什麼、哪些音總是不準。PitchCoach 要提供：

- 練習當下：即時調音器、長音與音階練習的客觀判定、伴奏（持續音、節拍器）。
- 練習之後：練習紀錄、30 天趨勢、可分享給老師的 PDF 週報。
- 後續追加：跟著伴奏的歌唱練習（音準與節奏判定）。

題目同時是一份技術作業，附帶明確的技術限制與可量化的驗收標準（AC-02～AC-21）。

---

## 1.2 使用者與情境

| 角色 | 情境 | 從情境推出的關鍵需求 | 來源 |
|---|---|---|---|
| 學生（兒童，小提琴／長笛） | 在家用家長的 iPhone 練習，常戴藍牙耳機聽伴奏 | 讀數穩定好懂、操作簡單、不會因來電或拔耳機而當掉 | 📄 `docs/ARCHITECTURE.md` §1.1 |
| 家長 | 協助開 App、傳報告給老師 | 一鍵產生 PDF 並分享 | 📄 同上 |
| 老師 | 上課時看 PDF 週報 | 看得出哪些音總是偏高或偏低、練習量是否足夠 | 📄 同上 |

「常戴藍牙耳機」這四個字在後續設計中影響很大：它帶來 150–250 ms 的輸出延遲，而且藍牙耳機有自己的麥克風。這兩點後來決定了收音路由（固定內建麥克風）、歌唱的時間對齊與延遲校正三個設計（見 03、08 章）。

> 🔍 推斷：「兒童」這個使用者特徵是音階「抖動規則」（D5）與調音器多重平滑的動機之一。設計文件 D5 的說明有提到「兒童的音在 ±15 邊界附近抖動很常見」，但平滑機制本身的設計理由文件中只寫了技術目的。

## 1.5 驗收標準：把「做完了」定義清楚

> 📄 依據：原始題目的 AC 清單；`docs/ARCHITECTURE.md` §1.4、`docs/SINGING_MODE.md` §1.3 的追溯表

好的驗收標準要可判定、可重現、指定驗證方式。題目的 AC 在設計階段被逐條補上「怎麼驗證、在哪裡驗證」（節錄）：

| # | 驗收標準 | 驗證方式 | 位置 |
|---|---|---|---|
| AC-02 | 純正弦 65–2,100 Hz 每半音、44.1k／48k，誤差 < 1 cent | 參數化單元測試 | `PitchDetectionTests` |
| AC-04 | 白噪音 SNR 20 dB 誤差 < 3 cents | 單元測試，固定亂數種子 | `PitchDetectionTests` |
| AC-06 | ≥ 500 組隨機頻率＋隨機泛音 | 性質測試，固定種子 | `MPMPropertyTests` |
| AC-08 | 延遲 ≤ 150 ms 並說明量測方式 | 內部時間戳＋外部慢動作錄影 | README（實機） |
| AC-10 | 到位判定 299／300 ms 邊界、±15 cents 抖動規則 | 單元測試 | `ScaleEvaluatorTests` |
| AC-11 | 三種音訊路由讀數差 ±3 cents，附截圖 | 實機手動 | README |
| AC-12 | 模擬來電／插拔耳機不當機、可恢復、標記中斷 | 狀態機單元測試＋實機手動 | `PracticeLifecycleTests`、README |
| AC-18 | 合成演唱訊號，起音誤差 < 30 ms | 整條鏈單元測試 | `OnsetDetectorTests` |

幾個改寫值得記住：

- **「SNR 20 dB」補上了噪音種類、頻率清單、單一 frame、固定種子。** 少了固定種子，測試會「今天過、明天不過」。
- **「持續 300 ms」改寫成 299 ms 不到位、300 ms 到位兩個案例。** 這逼著實作者回答「時間戳用什麼型別」，後來決定了整個系統用整數精度的 `Duration`（📄 `docs/ARCHITECTURE.md` §3.3）。
- **AC-08、AC-11、AC-12 在分析階段就標明「需實機」**，並列為需要使用者協助的項目（📄 `docs/ARCHITECTURE.md` §1.5）。最後也的確是在實機上才發現了練習頁無法恢復收音的問題（11 章）。

## 1.6 模糊需求的處理：決策表

題目看似具體，但開始寫程式就會發現許多句子沒辦法直接實作。設計文件把每個需要決定的地方標成 🔶，彙整成決策表，提出選項與建議，由使用者確認。

> 📄 依據：`docs/ARCHITECTURE.md` §16、`docs/SINGING_MODE.md` §12；對話中使用者對兩份決策表都回覆「照建議」

### 例一：長音的「準確率」怎麼算（D4）

題目只說「±10 cents 時間比例」。採用的定義：

| 項目 | 採用 | 理由（設計文件所述） |
|---|---|---|
| 計時起點 | 第一個有音高的 frame 起算 10 秒 | 不把反應時間算進去 |
| 偏差基準 | 相對目標音，不是最近的音 | 長音的目的就是對準目標 |
| ±10 判定 | \|c\| ≤ 10.0，含邊界 | 明確寫出邊界歸屬 |
| 分母 | 10 秒內全部 frame（無音高與錯音都算不在範圍） | 中途停掉不該拿高分 |
| 平均／標準差 | 只用有音高且 \|c\| ≤ 50 的 frame | 避免一個錯音把平均拉到數百 cents |
| 標準差 | 母體標準差（÷N） | 描述這 10 秒本身的穩定度 |

### 例二：音階到位遇到抖動（D5）

「±15 cents 持續 300 ms」遇到 14 ↔ 16 cents 的抖動怎麼辦？採用：範圍外的空檔 ≤ 50 ms 不重設計時，超過才重設。替代方案是嚴格重設（實作簡單、對學生嚴苛）。

### 例三：「練習分鐘數」的定義（D13，開發中追加）

> 📄 依據：對話中提出三個選項，使用者回覆「選 A」

長音一次只有 10 秒，若分鐘數只算長音與音階，一天練 20 次也才 3 分多鐘，圖表沒有意義。三個選項：記錄自由練習（採用）、只算長音與音階、算 App 開啟時間。採用後一併訂下細則：停頓 ≤ 5 秒計入、> 60 秒結束一段、少於 30 秒不記錄。

### 例四：同音連唱的節奏怎麼算（開發後期追加）

> 📄 依據：對話中使用者貼上的程式碼審查意見；使用者選擇「標『沒有分開唱』，不計入」

學生把〈小星星〉的「C C」連成一個長音、沒有重新咬字時，量不到第二個音的起音。選項：標示「沒有分開唱」且不計入節奏正確率（採用），或標示後算節奏不準。理由：量不到起音時算準或算錯都沒有依據，而且輕聲重新咬字也可能落在這一類。

## 1.7 需求變更：歌唱模式

> 📄 依據：`docs/SINGING_MODE.md` §1.1

追加歌唱模式時，先列出歌聲與樂器的差異，再推出每個差異對既有設計的影響：

| 差異 | 對設計的影響 |
|---|---|
| 顫音：每秒 5–7 次、±50 cents 以上 | 單一 frame 不能直接判定，需偵測顫音並取中心值 |
| 滑音：從下方滑進目標音 | 去頭尾各 15% 後取中位數 |
| 男生跟女生範唱會低一個八度 | 「容許八度」選項 |
| 母音共振峰讓高次泛音特別強 | 既有偵測器可能被誤導，可能要改共用的核心演算法 |
| 跟著伴奏唱 | 輸出與輸入共用時間軸，補償藍牙延遲 |
| 喇叭外放時麥克風收到伴奏 | 偵測器可能鎖定提示音 |

第四列是**風險**：如果偵測器真的會被共振峰誤導，就得修改樂器模式也在用的演算法。設計文件因此把「先寫人聲模擬測試」排成第一個里程碑 S1。結果 171 組人聲（3 種聲音 × 3 種母音 × 每個半音）都沒有八度錯誤，偵測器不需要修改（📄 commit `21bab7e`「test(S1): 人聲模擬訊號與共振峰風險驗證」）。
